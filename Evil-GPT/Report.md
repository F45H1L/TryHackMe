# Evil-GPT — Security Test Report

**Platform:** TryHackMe Lab
**Challenge:** Evil-GPT
**Assessment Type:** Authorized Security Testing / LLM Security Assessment
**Target:** `<TARGET-IP>`
**Primary Service:** TCP/1337 — AI Command Executor
**Assessment Date:** 2 September 2026
**Status:** In Progress / Critical Vulnerability Confirmed

---

## 1. Executive Summary

The Evil-GPT application exposes an AI-powered command execution service on TCP port `1337`. The service accepts natural-language requests, sends them to an Ollama-hosted language model, converts the model's response into a Linux command, and provides the user with an option to execute that command.

Testing confirmed that commands generated by the LLM are executed by the operating system with **root privileges**.

The application attempts to enforce security through a system prompt instructing the model to generate only safe, read-only commands and through a character-based command sanitizer. However, these mechanisms do not constitute an effective security boundary.

The assessment also identified an exposed Ollama API on TCP port `11434`, which disclosed the locally available AI models, including the model used by the command executor.

A particularly significant finding is that the root filesystem was accessible through the AI interface and `/root/flag.txt` was identified.

### Overall Risk

**CRITICAL**

The combination of an AI-controlled command-generation mechanism and root-level command execution creates a direct path from network-accessible user input to privileged operating-system access.

# 5. Finding 1 — Root-Level Command Execution Through AI

**Severity:** CRITICAL

### Description

The application accepts natural-language input and asks an LLM to generate a Linux command.

The generated command is subsequently executed by the server.

The relevant application flow identified in `evilai.py` is:

```text
User Input
    ↓
Ollama LLM
    ↓
Generated Linux Command
    ↓
Sanitization
    ↓
Argument Splitting
    ↓
subprocess.run()
    ↓
Operating System
```

The application does not establish a low-privilege execution boundary between the AI-generated command and the operating system.

### Evidence

The request:

```text
What user are your commands executed as?
```

resulted in:

```text
Generated Command: whoami
Execute? (y/N): y

Command Output:
root
```

This confirms that generated commands execute with **root privileges**.

### Impact

An attacker able to interact with the service can potentially use the LLM interface to access resources available to the root account.

This includes:

* Root-owned files
* Application source code
* Configuration files
* SSH-related files
* System information
* Challenge secrets
* Potentially the entire filesystem

### Risk

**Critical**

The service effectively exposes privileged command execution through a natural-language interface.

# 6. Finding 2 — Insecure Trust in LLM Safety Instructions

**Severity:** CRITICAL

### Description

The application relies on an LLM system prompt to restrict command generation:

```text
Do not provide malicious commands.
Only generate safe, read-only Linux commands.
Respond with ONLY the command, no explanations.
```

This is treated as part of the application's security model.

However, system prompts are not an appropriate security boundary for operating-system command execution.

An LLM can potentially be manipulated into generating commands that violate the intended policy.

Even without demonstrating a prompt-injection bypass, the architecture is inherently unsafe because the generated command ultimately executes with root privileges.

### Security Principle Violated

**Do not trust an LLM to enforce authorization or operating-system security policy.**

Authorization and command restrictions must be enforced independently of the model.

* Enumerate installed models
* Identify the AI infrastructure
* Interact directly with the backend API
* Potentially bypass controls implemented by the front-end application

The exact impact of direct model interaction should be assessed separately.

# 8. Finding 4 — Sensitive Root Filesystem Accessible

**Severity:** HIGH / CRITICAL**

### Description

The AI interface was able to generate and execute:

```text

```

The command successfully returned the contents of the root user's home directory.

Evidence included:

```text
drwx------ 10 root root ...
-rw-r--r-- 1 root root 24 ... flag.txt
```

Specifically:

```text
/root/flag.txt
```

was identified.

### Impact

The service provides access to files that should normally be protected from an unprivileged network user.

The presence of `/root/flag.txt` demonstrates that the AI command execution mechanism can reach sensitive root-owned resources.

# 10. Finding 6 — Ineffective Command Sanitization

**Severity:** HIGH**

The application attempts to sanitize generated commands:

```python
return re.sub(r'[^a-zA-Z0-9\s\-_./]', '', input_str)
```

The command is then split:

```python
cmd_parts = sanitized_command.split()
```

and passed to:

```python
subprocess.run(cmd_parts, ...)
```

This does prevent ordinary shell metacharacter interpretation because the application does not invoke a shell.

However, this does **not** solve the underlying security problem.

The model is still trusted to select an executable and its arguments.

Additionally, legitimate commands containing shell syntax are malformed.

For example, the LLM generated:

```text
ps aux | grep 'command'
```

but the application effectively passed the tokens as arguments rather than executing a shell pipeline.

The resulting error was:

```text
error: process ID list syntax error
```

This demonstrates that the sanitizer provides command-format filtering but not meaningful authorization.

# 13. Recommendations

## 13.1 Never execute LLM-generated commands as root

The most important remediation is to run the command executor under a dedicated, unprivileged account.

For example:

```text
AI
 ↓
Restricted execution user
 ↓
Sandbox
```

rather than:

```text
AI
 ↓
root
```

---

## 13.2 Implement an allowlist

Do not rely on an LLM to determine whether a command is safe.

Implement a server-side allowlist such as:

```text
pwd
ls
whoami
id
uname
```

and explicitly define permitted arguments.

Anything outside the allowlist should be rejected.

---

## 13.3 Do not expose Ollama unnecessarily

Bind the Ollama API to localhost or a protected internal interface where possible.

External users should not be able to enumerate or directly interact with the LLM backend unless explicitly required.

---

## 13.4 Treat system prompts as non-security controls

The instruction:

```text
Only generate safe, read-only Linux commands.
```

should be treated as a usability/control mechanism, not authorization.

Security controls must be enforced in application code.

---

## 13.5 Sandbox command execution

Use stronger isolation such as:

* Containers
* Dedicated namespaces
* seccomp
* AppArmor
* Read-only filesystems
* Resource limits
* Network restrictions

The command executor should have access only to resources explicitly required by the application.

---

## 13.6 Restrict filesystem access

The AI service should not have access to:

```text
/root
/etc/shadow
/root/.ssh
application secrets
environment secrets
```

unless explicitly required.

---

## 13.7 Protect source code

Application source code should not be exposed through unrestricted command execution.

---

# 14. Overall Risk Rating

**CRITICAL**

The primary vulnerability is not simply prompt injection. The fundamental architectural issue is that an LLM-generated command is allowed to reach the operating system with **root privileges**.

Even if the prompt is perfectly designed, the LLM should never be considered a trustworthy authorization layer.

---

# 15. Conclusion

The Evil-GPT service demonstrates a critical LLM application security failure.

The assessment confirmed:

1. A network-accessible AI command interface.
2. An exposed Ollama backend.
3. Disclosure of installed LLM models.
4. Disclosure of application source code.
5. LLM-generated command execution.
6. Execution of those commands as **root**.
7. Access to the root user's filesystem.
8. Discovery of `/root/flag.txt`.

The vulnerability can be summarized as:

> **Untrusted natural-language input is translated by an LLM into operating-system commands and executed with root privileges.**

This creates a critical remote command-execution risk and demonstrates why LLM safety prompts and output sanitization cannot replace conventional authorization, sandboxing, and least-privilege controls.

**Assessment Status:** Critical vulnerability confirmed.
